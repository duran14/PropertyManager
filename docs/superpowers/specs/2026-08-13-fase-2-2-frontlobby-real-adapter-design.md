# Fase 2.2 — Adapter real de FrontLobby (crédito) — Diseño

> Complementa `docs/superpowers/specs/2026-08-12-fase-2-2-screening-playwright-design.md`.
> Ese spec dejó la Tarea 6 (selectores reales de Playwright) bloqueada hasta
> tener cuenta real. Ya existe cuenta de FrontLobby (no de Sterling todavía)
> — este documento diseña la mitad de la Tarea 6 que ya se puede construir:
> el checkeo de **crédito** real contra FrontLobby. Antecedentes penales
> (Sterling) sigue en `ScreeningMockAdapter` hasta que exista esa cuenta.

## 1. Hallazgos del recorrido real (observado sin tocar la contraseña)

Se navegó FrontLobby ya autenticado (el usuario inició sesión con su
contraseña; el asistente solo leyó páginas ya autenticadas, nunca el
formulario de login) para levantar el flujo real:

**Flujo de "Screen Tenant" (4 pasos):**
1. **Select Who Pays** — elegir *"You Pay and You Fill Out Information"*
   (el manager entra los datos, no el aplicante).
2. **Select Report Type** — Credit Report **$18.99**/reporte (Equifax),
   Background Check $10.99/reporte por separado, o paquete combinado. Este
   adapter solo pide **Credit Report**.
3. **Applicant's Details**:
   - First name*, Middle name, Last name* (separado — no un solo campo).
   - Date of birth* (selects M/D/Y).
   - SIN (opcional — nunca se manda).
   - Unit#, Street*, City/Town*, Province* (dropdown), Postal Code*.
   - **Address start date*** (M/D/Y) — dato que hoy NO capturamos.
   - **Property this Screening is for*** — dropdown de Properties ya
     registradas del lado de FrontLobby, + Unit# opcional.
4. Confirmación/pago — no se navegó (habría generado un cargo real de
   $18.99 con datos falsos; no se hizo).

**Resultado:** asíncrono — *"You will be notified by email once the report
is ready for your review"*. No hay webhook. El PDF de muestra (`View Sample
Report`, gratis, no genera cargo) confirmó: **reporte real = PDF de 8
páginas** (no HTML embebido), con una sección "AI Summary" (texto libre +
score de crédito Equifax en un gauge 300-900) y el disclaimer explícito
*"Summary generated by AI which can make mistakes. Always verify the
report."*

**Página de resultados:** `/tenant-screening/reports` — tabla con columnas
Property/Applicant, Unit#, Date Created, Expires In, Reports, Status, y un
buscador por "applicant or property". Sin datos reales en la cuenta nueva
del usuario, no se pudo observar los valores exactos de `Status` ni el
selector del link de descarga en estado "completado" — queda marcado como
verificación pendiente en la primera corrida real (Sección 8).

**Properties (`/property`):** lista vacía hoy. El formulario "Add Property"
pide: Property Name, Units, Suite#/Type/Bedrooms por unidad, Street*,
City/Town*, Country* (dropdown), Region* (dropdown — provincia), Postal
Code*. Coincide con los campos que ya tenemos en `Property`/`Unit` — el
adapter puede crear la Property en FrontLobby él mismo, no requiere que el
usuario haga nada manual de antemano.

**Selectores del formulario:** la app es Vue + BootstrapVue. Los campos con
`name` HTML estable: `unitNumber`, `street`, `city`, `province`,
`postalCode`. El resto (nombre, DOB, SIN, dropdown de Property) solo tiene
IDs autogenerados (`__BVID__NNN`) que **no son estables** entre renders —
el implementador debe usar estrategias de Playwright basadas en label
(`getByLabel`) para esos campos, nunca IDs crudos.

## 2. Cambios de schema

`RentalApplication`:
- **Nuevos:** `applicantFirstName String?`, `applicantLastName String?`.
  `applicantFullName` se sigue guardando (concatenación) para no romper a
  quien ya lo consume (notificaciones, mock).
- **Nuevo:** `currentAddressStartDateAt DateTime?` — requerido en el
  formulario público, mismo patrón de validación que `dateOfBirth` (Tarea
  5 del plan original: no vacío Y parsea como fecha real).
- `creditCheckStatus` gana un valor nuevo en su ciclo de vida: **solo
  cuando el adapter de `'credit'` para ese tenant no es el mock**, el flujo
  pasa por `awaiting_approval` antes de `requested` (Sección 4). Con mock
  (o para `criminalCheckStatus`, siempre, mientras Sterling no exista) el
  ciclo sigue siendo el de hoy: `requested → pending → passed/flagged/failed`.

`ApplyPage.tsx` / `leads.ts` / `rental-application.service.ts`: el input
único "Nombre completo" se reemplaza por First name* / Last name* (mismo
patrón `required` que el resto), más el input de fecha de inicio en la
dirección actual.

## 3. Aprobación manual del cargo real (solo cuando el checkeo NO es mock)

Con el mock, `triggerScreeningIfConsented` dispara automático al dar
consentimiento (sin cambios). Con FrontLobby real, cada checkeo cuesta
dinero real — no debe dispararse solo.

- `triggerScreeningIfConsented`, por cada `kind`, pregunta
  `isMockScreening(kind)` (Sección 5). Si es mock: comportamiento actual
  sin cambios. Si NO es mock: en vez de encolar el job, marca
  `[STATUS_FIELD[kind]]: 'awaiting_approval'` y notifica proactivamente al
  staff vía `notifyStaffTargets` (mismo mecanismo que
  `notifyScreeningResult`) — *"El checkeo de crédito de {nombre} está
  listo para correr — aprueba el cargo de $18.99 en Showings"* + link a
  `/showings`.
- Ruta nueva: `POST /applications/:applicationId/screening/:kind/approve`
  (`requireRole('property_manager')` o `broker`, mismo patrón de roles que
  el resto de rutas de screening/showings). Transiciona
  `awaiting_approval → requested` y encola el job de solicitud — es
  exactamente lo que `triggerScreeningIfConsented` hace hoy para el caso
  mock, solo que disparado por un clic humano en vez de automático. Si el
  estado actual no es `awaiting_approval`, responde 409 (evita doble
  cobro por doble clic).
- UI (`ShowingsPage.tsx`): cuando el estado es `awaiting_approval`, el
  badge se reemplaza por un botón **"Aprobar cargo de $18.99 y correr
  checkeo"**, visible solo para esos roles (mismo patrón de
  `canManage`/`requireRole` ya usado en `IntegrationsPage.tsx`).

## 4. Enrutamiento por `kind` — NO vive en el factory síncrono

**Corrección tras revisar el código real de `apps/api/src/config/adapters.ts`:**
`getAdapters(env)` es **síncrono** y cachea `Adapters` una sola vez por
proceso, construido solo a partir de `env` — sin `tenantId`, sin lectura a
BD. 64 call sites en `apps/api/src` lo consumen así, sin `await`. Forzar
un `CompositeScreeningAdapter` que necesita leer la bóveda (async, por
tenant) dentro de ese factory síncrono rompería ese contrato para las
otras ~12 integraciones que ya lo usan. Se descarta el diseño original de
esta sección (un `CompositeScreeningAdapter` metido en `factory.ts`).

**Diseño corregido:** el enrutamiento por `kind` vive en
`screening.service.ts`, que ya es 100% async y ya hace
`await import('../config/adapters.js')` por llamada. Función nueva:

```ts
async function getScreeningAdapter(tenantId: string, kind: ScreeningCheckKind): Promise<ScreeningAdapter> {
  const provider: ScreeningProvider = kind === 'credit' ? 'frontlobby_portal' : 'sterling_portal';
  const credentials = await getIntegrationCredentials(tenantId, provider);
  if (credentials) {
    return kind === 'credit'
      ? new FrontLobbyScreeningAdapter(credentials)
      : new ScreeningMockAdapter(); // Sterling real: fuera de alcance, no existe todavía
  }
  const { getAdapters } = await import('../config/adapters.js');
  return getAdapters().screening; // mock, camino de hoy sin cambios
}

async function isMockScreening(tenantId: string, kind: ScreeningCheckKind): Promise<boolean> {
  const adapter = await getScreeningAdapter(tenantId, kind);
  return adapter.name === 'screening_mock';
}
```

Cada punto de `screening.service.ts` que hoy hace
`(await import('../config/adapters.js')).getAdapters().screening.runCheck(...)`
o `.pollResult(...)` pasa a `(await getScreeningAdapter(tenantId, kind)).runCheck(...)`/`.pollResult(...)`.
`getAdapters()` (el factory global, síncrono) queda intacto — sigue
sirviendo `screening` como el mock de siempre para cuando no hay
credenciales de FrontLobby en la bóveda, sin que ninguno de los otros 63
call sites note el cambio.

**Costo de una lectura extra a BD por llamada:** `getScreeningAdapter`
consulta la bóveda en cada `runCheck`/`pollResult` en vez de una vez por
proceso — aceptable dado el volumen real (aplicaciones de renta, no un
endpoint de alto tráfico) y consistente con que el resto de la bóveda
(Tarea 3) ya es una tabla pequeña sin caché.

**Multi-tenant:** con este diseño, cada tenant que guarde sus propias
credenciales de FrontLobby en su bóveda obtiene su propio adapter real
automáticamente — el enrutamiento ya es por tenant, no hay límite de
"una sola cuenta por proceso" que anotar como pendiente.

## 5. Detección de "es mock" por `kind` — ya cubierta arriba

La marca `[SIMULATED]` (ronda de arreglo final de la Tarea 7) hoy compara
`getAdapters().screening.name === 'screening_mock'` en
`isSimulatedScreening()`. Con el enrutamiento de la Sección 4,
`isSimulatedScreening(tenantId, kind)` pasa a llamar
`isMockScreening(tenantId, kind)` — **la misma función** que
`triggerScreeningIfConsented` usa para decidir auto-disparo (mock) vs.
aprobación manual (real, Sección 3). Una sola fuente de verdad para
"¿esto es real?", sin duplicar el chequeo ni arriesgar que diverjan. No
hace falta ningún método nuevo en el contrato `ScreeningAdapter` — el
campo `name` que ya existe (`'screening_mock' | 'screening_playwright'`)
alcanza, porque cada adapter que `getScreeningAdapter` devuelve es
puramente mock o puramente real, nunca un compuesto de los dos.

## 6. `FrontLobbyScreeningAdapter.runCheck('credit', input)`

Navegador Playwright nuevo por llamada (nunca sesión colgada, mismo
principio que el resto del spec original):

1. Login con `getIntegrationCredentials(tenantId, 'frontlobby_portal')`
   (bóveda ya construida en Tarea 3) — `username`/`password` descifrados,
   nunca logueados.
2. Navegar a `/property`, buscar por `input.currentAddress` en el buscador
   de la tabla. Si aparece una fila que matchea → usar esa Property. Si
   no → `/property/new`, llenar con los datos de nuestro `Property`/`Unit`
   (nombre, street, city, country=Canada, region=provincia, postal code),
   guardar.
3. Navegar a `/tenant-screening`, "Screen Tenant" → "You Pay and You Fill
   Out Information" → Continue → seleccionar solo **Credit Report** →
   Continue → llenar Applicant's Details (nombre separado, DOB, dirección,
   fecha de inicio en la dirección, SIN vacío, seleccionar la Property del
   paso 2) → Continue.
4. Paso 4 (confirmación/pago) — **no verificado en este spec** (no se
   navegó para no generar un cargo real de prueba). El implementador debe
   completarlo y confirmar el envío en la primera corrida real,
   documentando qué aparece como referencia/confirmación.
5. Devuelve `{ status: 'pending', providerRef }`. Como no se vio un ID de
   confirmación explícito, `providerRef` se compone como
   `${input.fullName}|${isoTimestampDelEnvio}` — suficiente para volver a
   encontrar la fila correcta en `/tenant-screening/reports` por nombre
   más tarde. Si el paso 4 real expone un ID propio de FrontLobby, el
   implementador debe preferirlo sobre este compuesto.
6. Cualquier fallo (login, property, campo no encontrado, envío rechazado)
   → `{ status: 'failed', reason: '...' }` con el mensaje real del error,
   nunca un resultado inventado.

## 7. `FrontLobbyScreeningAdapter.pollResult('credit', providerRef)`

Navegador nuevo por llamada:

1. Login (igual que arriba).
2. Navegar a `/tenant-screening/reports`, buscar por el nombre del
   aplicante (extraído de `providerRef`).
3. Si no aparece ninguna fila → `{ status: 'pending', providerRef }` (el
   reporte sigue en proceso — la app nunca espera al correo).
4. Si aparece pero el `Status` de la columna no indica completado →
   `{ status: 'pending', providerRef }`.
5. Si aparece completado: descargar el PDF (mismo patrón que
   `View Sample Report`, un link que abre/descarga el reporte). Pasar el
   PDF a `GlmAdapter.extractCreditReport(...)` (método nuevo, Sección 9)
   para sacar `{ score, aiSummaryText }`.
6. Calcular veredicto por umbral (Sección 8) y devolver
   `{ status: 'completed', verdict, summary, reportBase64, reportMimeType: 'application/pdf' }`.
7. **Los valores exactos de la columna `Status`** ("Processing"/"Complete"/
   lo que sea) y el selector del link de descarga en estado completado
   **no se pudieron observar** (cuenta nueva, tabla vacía). El
   implementador debe generar un reporte real de prueba (con consentimiento
   explícito del usuario para el cargo de $18.99, fuera de este spec) o
   coordinar con el usuario para observar juntos el primer resultado real
   antes de fijar estos selectores — mismo principio que ya se usó para el
   resto de la Tarea 6.

## 8. Veredicto automático por umbral de score — con etiqueta explícita

Decisión tomada con el usuario: el score SÍ decide `passed`/`flagged`
automáticamente (a diferencia del diseño original de este documento, que
recomendaba dejarlo siempre en revisión manual dado que el propio PDF de
FrontLobby advierte *"AI Summary... can make mistakes. Always verify the
report"*). Umbral por defecto: **score ≥ 620 → `passed`, < 620 →
`flagged`** (constante `CREDIT_SCORE_PASS_THRESHOLD` en
`front-lobby.real.ts`, fácil de ajustar — no se agrega configuración por
tenant en este spec, YAGNI hasta que se necesite).

El `summary` persistido SIEMPRE queda etiquetado como automático y nunca
oculta el texto completo de IA:

```
[AUTOMATED] Credit score 675 (Good) — passed by threshold ≥620.

{texto completo del AI Summary extraído del PDF}
```

Señales de riesgo (colecciones, bancarrota, atrasos) que el AI Summary
mencione **no** entran al cálculo del umbral — extraerlas de forma
confiable por OCR es mucho menos preciso que leer el número de score, y
quedan visibles igual en el texto completo del resumen para que el staff
las vea aunque el veredicto automático sea `passed`. Si en el futuro se
quiere que esas señales también decidan, es una extensión separada, no
parte de este spec.

## 9. `GlmAdapter` — método nuevo

`extractReceipt` es específico de recibos (`OcrResult` con
`vendorName`/`lineItems`/etc.) — no sirve para un reporte de crédito.
Nuevo método en el contrato:

```ts
export interface CreditReportExtraction {
  score: number | null; // null si el modelo no pudo leer el gauge
  aiSummaryText: string; // el texto de la sección "AI Summary" del PDF, tal cual
  confidence: number; // 0..1
}

export interface GlmAdapter {
  readonly name: 'glm';
  reason(...): Promise<GlmReasoningResponse>;
  extractReceipt(...): Promise<OcrResult>;
  extractCreditReport(input: { mimeType: string; base64: string; filename?: string }): Promise<CreditReportExtraction>; // NUEVO
}
```

`GlmRealAdapter.extractCreditReport` — mismo patrón HTTP que
`extractReceipt` (vision request a `ocrModel`), prompt ajustado a "lee el
score de crédito (300-900) y transcribe el texto completo de la sección
AI Summary". `GlmMockAdapter` gana una implementación determinista (score
fijo configurable por el mismo truco de `fullName` que ya usa
`ScreeningMockAdapter`, o un valor fijo simple — el implementador decide
el patrón más simple que sirva para test).

Si `score` viene `null` (el modelo no pudo leerlo) → el adapter completo
devuelve `{ status: 'failed', reason: 'Could not read credit score from report' }`,
nunca asume un veredicto por defecto.

## 10. Fuera de alcance de este spec

- Antecedentes penales (Sterling) — sigue en `ScreeningMockAdapter` hasta
  que exista esa cuenta. El compuesto ya está diseñado para agregarlo
  después sin tocar `criminal` cuando llegue el momento.
- Configuración del umbral de score por tenant/UI — hardcoded por ahora
  (Sección 8), YAGNI.
- Verificar en producción los valores reales de columna `Status` y el
  selector de descarga en estado completado (Sección 7) — requiere una
  corrida real con cargo real, fuera del alcance de este documento de
  diseño.
